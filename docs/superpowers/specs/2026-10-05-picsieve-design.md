## 1. 这是什么

一个 Windows 桌面工具，用来清理本地大批量的 Pixiv 图片：找出重复图、按条件筛出不要的图、安全地删掉它们。

目标用户就是本机使用者本人：图片总量十几万张、全部平铺在少数几个大文件夹里，Windows 资源管理器已经无法正常管理（打开就卡）。

### 要解决的问题，按优先级

1. **重复**——同一张图存了多份，或同一幅画有不同尺寸／格式的版本。
2. **不要的图**——灰阶（黑白灰）图、画面过小的图。
3. **删得安全**——十几万张图，误删不可接受。
4. **能用**——十几万张缩略图要能流畅翻、能按条件即时筛。

### 文件名规律（实测）

绝大多数文件名带 Pixiv 作品 ID 和画师名，但写法不统一：


## 3. 已确认的需求

以下每一条都经用户逐条确认。

### 3.1 查重复：三档都要

| 档 | 定义 | 处理方式 |
|---|---|---|
| **一模一样** | 文件内容逐字节相同 | 自动保留一张，其余标记为待删 |
| **同一张画的不同版本** | 画面视觉相同，但尺寸／格式／压缩不同 | **只列出，不自动删**，由用户确认 |
| **看着像但拿不准** | 相似度较低 | 按相似度从高到低排队，用户逐组过 |

### 3.2 按条件筛选并删除

筛选维度至少包含：分辨率（短边／长边）、文件体积、格式、是否灰阶、是否重复、是否解码失败。

**阈值不预设死。** 软件内提供可调控件（滑块／输入框），拖动时实时显示「按当前条件会命中多少张」。

### 3.3 「不要的图」的判定

- **灰阶图**：画面基本为黑白灰者视为不要。判定结果在界面上以角标标出，**删除前必须给用户看预览**。
- **偏小的图**：由用户在界面里自行设定阈值（实测数据已证明用户感觉中的「很多小图」实际是 600–1200 px 段，占 53%，需要用户自己划线）。

### 3.4 删除的安全边界

采用**隔离区**方案：

- 所有删除动作都是把文件**移动**到 `D:\色图\_待确认删除\`。
- 同一块盘上移动是原子重命名，瞬间完成，不复制、不额外占用空间。
- 保留原始路径记录，可随时搬回。
- 「彻底清空」需二次确认，并明确显示将永久删除的文件数与释放空间。
- 扫描与指纹阶段**全程只读**。

### 3.5 长期使用

- 软件是长期工具，以后新增的图接着跑。
- 已算过的图不重算（依据文件大小 + 修改时间判断）。
- 扫描结果持久化在本地数据库。

### 3.6 主界面形态

采用**图库式**：左侧筛选栏、中间缩略图网格、底部操作栏。另配「重复组」视图，一组一组过。

## 4. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 应用框架 | **Tauri 2** | 安装包小、内存占用低、原生窗口；符合本机既有技术栈偏好 |
| 后端语言 | **Rust** | 图像解码、哈希计算、目录遍历都是 CPU／IO 密集活，Rust 能直接吃满 16 核 |
| 前端 | **Vue 3 + TypeScript + Vite** | 与既有项目一致 |
| 并行 | **rayon** | 数据并行，线程数可配 |
| 图像解码 | **image** crate | 覆盖 JPEG／PNG／GIF |
| 内容指纹 | **BLAKE3** | 多线程下吞吐可达数 GB/s，且 256 位抗碰撞，不会把两张不同的图误判为相同 |
| 视觉指纹 | **pHash（DCT 感知哈希，64 位）** | 对缩放、重压缩、轻微改色稳定 |
| 数据库 | **SQLite（rusqlite，bundled）** | 单文件、零依赖、支持索引与事务 |
| 目录遍历 | **jwalk**（并行遍历） | 十几万文件的枚举需要并行才快 |
| 打包 | **Tauri NSIS 安装包** + 免安装 zip | 兼顾两种使用习惯 |

### 关于 Python sidecar

本机既有技术栈偏好是「Tauri 2 + Vue 3 + Python sidecar」，但**本项目不使用 Python sidecar**，理由：

1. 图像解码、哈希、灰度判定在 Rust 侧有成熟且更快的库（`image` + `rayon`），Python 侧做同样的事更慢，还要跨进程搬运数据。
2. 引入 sidecar 会显著增加打包与分发复杂度（PyInstaller/Nuitka 产物体积、路径、杀软误报）。
3. 本项目的数据处理是「一次读入、算完落库」，没有需要 Python 生态（numpy/pandas 等）的场景。

若后续出现必须用 Python 的环节（例如机器学习模型推理），再以 sidecar 形式追加，并在那时更新本规格。

## 5. 架构与模块

单一进程，内部按职责分模块，模块之间通过明确的接口通信。

```
┌──────────────────────────────────────────────┐
│  前端（Vue 3，WebView2）                      │
│  图库网格 / 筛选栏 / 重复组视图 / 隔离区      │
└───────────────┬──────────────────────────────┘
                │ Tauri IPC（命令 + 事件）
┌───────────────┴──────────────────────────────┐
│  后端（Rust）                                 │
│                                               │
│  scanner    目录遍历、读元数据与图片头         │
│  fingerprinter  内容指纹 / 视觉指纹 / 灰度     │
│  grouper    重复分组                          │
│  query      筛选查询（SQL）                    │
│  thumbs     缩略图缓存                        │
│  quarantine 隔离区：移入 / 搬回 / 清空        │
│  db         SQLite 访问层                     │
└──────────────────────────────────────────────┘
```

### 各模块职责（每个模块都能独立理解和测试）

| 模块 | 做什么 | 依赖 | 对外接口 |
|---|---|---|---|
| `scanner` | 遍历目录，取文件大小、修改时间、图片宽高、格式；不读图片内容 | `jwalk`、`image`（仅读头） | `scan(roots) -> 事件流（进度、新增、变更、失败）` |
| `fingerprinter` | 对文件算内容指纹、视觉指纹、灰度分数 | `blake3`、`image`、`rayon` | `fingerprint(file_ids) -> 结果流` |
| `grouper` | 依据指纹把文件分组 | `db` | `group_exact()`、`group_similar(threshold)` |
| `query` | 按条件组合筛选文件 | `db` | `query(filter) -> 文件列表（分页）` |
| `thumbs` | 生成并缓存缩略图 | `image` | `thumb(file_id) -> 图片字节` |
| `quarantine` | 移入隔离区、搬回、彻底清空 | 文件系统 | `move_in(ids)`、`restore(ids)`、`purge(batch)` |
| `db` | SQLite 表结构与查询 | `rusqlite` | 各模块共用的数据访问 |

## 6. 数据模型

SQLite 单文件，放在 `%LOCALAPPDATA%\PicSieve\picsieve.db`。

```sql
CREATE TABLE files (
  id                INTEGER PRIMARY KEY,
  path              TEXT NOT NULL UNIQUE,   -- 绝对路径
  root              TEXT NOT NULL,          -- 所属扫描根目录
  size              INTEGER NOT NULL,
  mtime             INTEGER NOT NULL,       -- 修改时间（秒）
  ext               TEXT,                   -- 小写扩展名
  format            TEXT,                   -- 解码器识别出的真实格式
  width             INTEGER,
  height            INTEGER,
  short_side        INTEGER,                -- MIN(width, height)，写入时算好，供索引使用
  pid               INTEGER,                -- 从文件名提取的 Pixiv 作品 ID
  artist            TEXT,                   -- 从文件名提取的画师名（尽力而为，可能为空）
  content_hash      TEXT,                   -- BLAKE3
  phash             TEXT,                   -- 64 位 pHash，十六进制
  gray_score        REAL,                   -- 灰度分数，越小越接近黑白灰
  decode_error      TEXT,                   -- 解码失败原因，NULL 表示正常
  scanned_at        INTEGER,
  fingerprinted_at  INTEGER,
  status            TEXT NOT NULL DEFAULT 'normal'  -- normal | quarantined | missing
);
CREATE INDEX idx_files_size       ON files(size);
CREATE INDEX idx_files_short_side ON files(short_side);
CREATE INDEX idx_files_content    ON files(content_hash);
CREATE INDEX idx_files_phash      ON files(phash);
CREATE INDEX idx_files_pid        ON files(pid);

CREATE TABLE dup_groups (
  id          INTEGER PRIMARY KEY,
  kind        TEXT NOT NULL,      -- exact | similar
  keep_file_id INTEGER,           -- 建议保留的文件；NULL 表示待用户决定
  created_at  INTEGER
);

CREATE TABLE dup_members (
  group_id  INTEGER NOT NULL,
  file_id   INTEGER NOT NULL,
  distance  INTEGER,              -- 与组内基准的汉明距离；exact 组为 0
  PRIMARY KEY (group_id, file_id)
);

CREATE TABLE quarantine (
  id              INTEGER PRIMARY KEY,
  file_id         INTEGER NOT NULL,
  original_path   TEXT NOT NULL,
  moved_path      TEXT NOT NULL,
  batch_id        TEXT NOT NULL,   -- 同一次操作的批次
  moved_at        INTEGER,
  restored_at     INTEGER
);

CREATE TABLE scan_roots (
  id    INTEGER PRIMARY KEY,
  path  TEXT NOT NULL UNIQUE,
  added_at INTEGER
);

CREATE TABLE delete_log (
  id          INTEGER PRIMARY KEY,
  path        TEXT NOT NULL,
  size        INTEGER,
  purged_at   INTEGER,
  batch_id    TEXT
);
```

写入全部走事务，保证断电后数据库不处于半写状态。

## 7. 处理流程

### 7.1 摸底扫描

1. 遍历用户指定的根目录，得到文件列表。
2. 对每个文件读取：大小、修改时间、扩展名；再用 `image` 只读图片头得到真实格式与宽高。
3. 与数据库中已有记录比对：`size` 和 `mtime` 都没变则跳过（增量）。
4. 落库，产出进度事件。

实测基线：13.7 万文件 82 秒（Python + Pillow）。Rust 并行遍历应当更快，性能目标定为 **≤ 2 分钟**。

**只处理图片文件**：扩展名属于 `jpg / jpeg / png / gif / webp / bmp` 的才入库；其他文件（本批里有 1 个 `.db`）只计数、不入库、不碰它。

**从文件名提取信息（尽力而为）**：

- **作品 ID**：优先匹配 `[pid=数字]` 或 `pid=数字`（不分大小写）；找不到则匹配被分隔符包围的 6–12 位数字串；仍找不到就留空。
- **画师名**：当文件名形如 `#名次 - 标题 - 画师 - [pid=…] -` 时取倒数第二段；形状不符则留空。

提取失败只影响界面显示和「同作品多页」这条辅助判断，**不参与任何自动删除决策**。

### 7.2 指纹计算

分两遍，都是并行，线程数可配（默认 = 逻辑核心数 − 2，给界面留出响应余量；本机为 32 − 2 = 30）。

**第一遍·内容指纹（快）**

1. 按 `size` 对所有未算过的文件分组。**大小不同的文件绝不可能逐字节相同**，所以大小为 1 的组直接跳过。
2. 组内文件才读取内容、算 BLAKE3。
3. 结果落库。

这一步的关键优化在于：用户的数据有 61,432 种尺寸组合，大部分文件大小唯一，因此绝大多数文件根本不需要读内容。实际读取量远低于 282 GB。

**第二遍·视觉指纹与灰度（慢）**

1. 对每个文件解码为缩略图（长边约 64 px）。
2. 算 64 位 pHash。
3. 同时算灰度分数：把缩略图转为 RGB，逐像素取三个通道两两差值的最大值，取 95 分位作为 `gray_score`。分数越小越接近黑白灰。
4. GIF 只取第一帧。
5. 解码失败的文件记录 `decode_error`，不中断整体流程。

**断点续算**：进度通过 `fingerprinted_at` 落库，中途退出后重跑只处理未完成的文件。

### 7.3 分组

**一模一样组（exact）**：按 `content_hash` 分组，组内多于一个文件即成组。建议保留规则：优先保留文件名含作品 ID 的、其次保留路径更短的、再其次保留修改时间更早的（该规则在界面上可改）。

**相似组（similar）**：按 pHash 的汉明距离聚类，阈值默认 `≤ 8`（64 位中最多 8 位不同），可调 0–16。每组的基准成员取组内「与其他成员平均距离最小」的那张，各成员到基准的距离记入 `dup_members.distance`，界面按这个距离排序展示。

**防误伤规则（重要）**：

- 若两张图的 `pid` 相同、且文件名中的页码信息不同，则判为**同一作品的不同页**，不进入相似组。本批文件的 `#N` 是排行榜名次而非页码，因此该规则仅依据 pid 与 `_p数字` 片段判断；信息不足时不做该判定，交由用户人工确认。
- 若一张图与另一张的 `pid` 相同但文件内容完全不同，则不视为重复（同一作品的不同图）。

### 7.4 界面操作

筛选查询直接走 SQL，带索引，目标响应 ≤ 100 ms。条件包含分辨率区间、体积区间、格式、灰阶、是否重复、是否解码失败，另支持按路径／文件名模糊搜索。

## 8. 判定规则汇总

| 判定 | 方法 | 默认阈值 | 可调 |
|---|---|---|---|
| 一模一样 | BLAKE3 内容指纹相同 | 精确匹配 | 否 |
| 视觉相似 | 64 位 pHash 汉明距离 | ≤ 8 | 是（0–16） |
| 灰阶 | 缩略图 RGB 通道差 95 分位 | ≤ 8 | 是 |
| 偏小 | 短边像素 | 不预设 | 是（滑块） |
| 同一作品不同页 | pid 相同 + 页码不同 | —— | 否 |

### 9.6 应用图标

图标 = 「经典圆角」底板 + 纯白漏斗图形。

> **本节是定稿。** 实现时按下面的参数与 `tools/make_icon.py` 产出即可，**不要另行设计图形、不要更换配色、不要改回正圆角**。确实需要改动时，先改本节并写明理由，再动代码。

**底板形状（经典圆角 / LegacyRounded）**

- 画布为边长 S 的正方形。
- 圆角半径 **r = 0.35 S**。
- 圆角曲线为**超椭圆**，指数 **n = 4**，参数方程：

  ```
  x = cx + r · sign(cos θ) · |cos θ|^(2/n)
  y = cy + r · sign(sin θ) · |sin θ|^(2/n)
  ```

- **为什么用 n = 4 而不是正圆角**：正圆角相当于 n = 2，它的曲率在与直边衔接处从「弯」突变到「直」，视觉上会出现一道不易察觉的折感；n = 4 时圆角在靠近直边处更快变平，直线与曲线的过渡是一阶导连续的，看上去更顺。这是用户明确指出的问题，不得改回正圆角。
- **出处**：SnowDesktop 项目 `src/icon_beautify.cpp` 中的 `kLegacyCornerRadiusRatio = 0.35f` 与 `kLegacyCornerExponent = 4.0f`（MIT 许可，其形状目录改编自 DeskMakeover 的 dm-icon-core shape catalog）。本项目**只采用其几何参数，不复制其任何图形**。
- 样式参考图的本地副本存放在 `docs/reference/icon-reference.png`。它是第三方软件的截图，**不纳入版本库**（已写入 `.gitignore`），仅作本地比对用。

## 10. 安全机制

1. **只读原则**：摸底与指纹阶段只读文件，不写、不移动、不改名。
2. **删除即移动**：所有删除都是移动到隔离区，且优先使用同盘原子重命名。
3. **跨盘兜底**：隔离区与源文件不同盘时，走「复制 → 校验内容指纹 → 删除源文件」，校验不通过则中止并保留原文件。
4. **操作日志**：每次移入、搬回、清空都写入 `delete_log`，可追溯。
5. **二次确认**：彻底清空需明确确认，且展示文件数与空间。
6. **失败不连锁**：单个文件出错只记录该文件，不影响整批操作。
7. **数据库事务**：所有写入在事务内完成，断电不会留下半写状态。
8. **隔离区自动排除**：设置隔离区目录时校验它不在任何扫描根目录之内或之下，避免下次扫描把待删文件又捞回来，形成循环。

## 11. 性能目标

| 项目 | 目标 |
|---|---|
| 摸底扫描（13.7 万文件） | ≤ 2 分钟 |
| 首次指纹计算 | ≤ 15 分钟 |
| 增量（新增 1,000 张） | ≤ 30 秒 |
| 筛选查询响应 | ≤ 100 ms |
| 缩略图网格滚动 | 稳定 60 fps |
| 内存占用 | ≤ 1.5 GB（61.7 GB 物理内存下有充足余量） |

依据：本机 16 核 32 线程 + PCIe 4.0 SSD，实测摸底 82 秒；内容指纹因按大小预筛而大幅减少实际读取量；视觉指纹受解码吞吐限制，按 30 线程估算应落在 15 分钟内。**以上为目标值，需在实现后用真实数据实测校准。**

## 12. 错误处理

| 情况 | 处理 |
|---|---|
| 单个文件解码失败 | 记录 `decode_error`，跳过，继续；界面可筛出「读不出的」 |
| 图片头损坏（实测本批有 2 个） | 同上 |
| 文件在扫描后被改名／删除 | 标记 `status = missing`，界面提示，不报错中断 |
| 文件被其他程序占用 | 重试 3 次（间隔 200 ms），仍失败则记录并跳过 |
| 磁盘空间不足（移入隔离区时） | 同盘移动不占空间；跨盘时先校验剩余空间，不足则中止该批 |
| 数据库损坏 | 提示重建索引；原始图片不受影响 |
| 权限不足 | 记录并跳过该文件，汇总在任务结束时提示 |

## 13. 测试策略

- **单元测试（Rust）**：文件名解析（三种作品 ID 写法、表情符号、空文件名）、BLAKE3 一致性、pHash 对「缩放／重压缩后仍相似」的稳定性、灰度分数对已知彩图与灰图的区分、同盘移动与跨盘移动的逻辑分支。
- **集成测试**：构造一个受控的小图片集，包含已知的一模一样组、相似组、灰阶图、同作品多页、损坏文件、非图片文件，验证扫描 → 指纹 → 分组 → 隔离全流程结果与预期一致。
- **性能测试**：用真实目录的副本（或抽样 1 万张）验证吞吐与内存。
- **手工冒烟**：安装包在真机跑通扫描 → 筛选 → 隔离 → 搬回 → 清空。
- **破坏性验证**：在隔离区方案上专门验证「移入后能完整搬回」且内容指纹不变。

## 14. 明确不做的事

- 不做图片编辑（裁剪、调色、压缩）。

- 不支持 macOS／Linux。本期只做 Windows。
- 不做多用户／权限体系。

## 15. 风险与未验证项

| 风险 | 说明 | 应对 |
|---|---|---|
| 视觉相似误判 | pHash 可能把不同作品判为相似 | 相似组**不自动删**，全部人工确认；阈值可调；支持按相似度排序从最像的开始看 |
| 灰度误判 | 偏灰的彩色插画可能被误判 | 删除前强制预览；阈值可调；界面上标明分数 |
| 内容指纹的读取量 | 若尺寸重复度高，需读取的数据量会上升 | 已用大小预筛规避；实现后按真实数据实测 |
| QLC 固态寿命 | 隔离区在跨盘时会有大量写入 | 默认隔离区与源同盘，走原子重命名，几乎无写入 |
| 「几十上百万张」的规模 | 当前实测为 13.7 万张，百万级未验证 | 数据访问全部走索引与分页；实现后用 2 倍、10 倍规模的合成数据压测 |
| 需求漂移 | 用户后续可能想加「自动整理目录」等 | 模块边界已按职责切分，追加不影响核心判重逻辑 |
