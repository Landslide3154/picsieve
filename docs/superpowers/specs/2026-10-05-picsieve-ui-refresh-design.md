- 状态：已与用户逐条确认（本轮范围、交互方式、规范技能均经用户勾选）
- 依据：`docs/superpowers/specs/2026-10-05-picsieve-design.md`（主规格）、

## 1. 用户提出的问题（原话归纳）

1. 选中框细、暗蓝、不显眼 —— 要求选中后「凸出来」或有特效
2. 双击图片应该用系统默认看图软件打开
3. 鼠标悬停时应显示图片信息
4. 分辨率与文件体积两个滑块「逻辑不明」
5. 拖滑块时卡顿
6. 筛选条件即时生效是否是卡顿原因？是否该改成点「应用」才生效
7. 让我自己总结其余页签在易用性/美观性上的不足并优化
8. 要求参考网络上优秀的 UI/逻辑规范

**用户补充要求：** 悬停也要有放大悬浮特效；悬停后点击选中要把特效「固定」下来；悬停、移开、选中之间的过渡都要有动画。

## 2. 已确认的决定

| 决定 | 结论 |
|---|---|
| 筛选生效方式 | **不加「应用」按钮**。拖动时实时更新「命中 N 张」，松手/停顿 250ms 后才刷新图片墙 |
| 本轮范围 | 用户勾选了全部 8 项（无限滚动、真取消、顶栏搜索排序统计、条件摘要、隔离区展开、重复组省钱与一键、快捷键、样式统一） |
| 规范技能 | 已装 `web-design-guidelines`（全局 `~/.dsh/skills`） |

## 3. 各区域设计

### 3.1 图库（ThumbCell / ThumbGrid）

- **悬停**：`translateY(-2px)` + 阴影加深，120ms 过渡
- **选中**：`scale(1.045)` 且更高层级、白色内圈 + 亮蓝外圈双描边（保证在浅色和深色照片上都看得清）、
  投影、右上角亮蓝圆勾标；底色叠一层极淡的蓝
- **过渡**：悬停/离开/选中/取消选中全部走同一套 120ms `transform`+`box-shadow` 过渡，
  遵循 `prefers-reduced-motion`（该媒体查询下不放大、只保留描边）
- **悬停信息卡**：文件名（单行省略）、尺寸、体积、格式、作品 ID、画师、灰阶分数、重复数量，
  末行写明「双击打开 · 右键更多」；卡片贴在格子底部，`pointer-events: none` 避免闪烁
- **双击**：调用系统默认程序打开原图（Rust 侧 `open_external`）
- **右键菜单**：打开、在资源管理器中显示、复制路径、选中/取消选中、移到隔离区
- **无限滚动**：每批 300 条，滚动到距底部 1.5 屏时自动取下一批；到底后显示「已经到底了」
- **快捷键**：`Ctrl+A` 全选当前结果、`Esc` 取消选择 / 关闭预览、`空格` 大图预览、
  `方向键` 移动焦点格、`Enter` 打开、`Delete` 移入隔离区
- **空格预览**：内置大图浮层（原始尺寸缩放显示 + 尺寸/体积/路径），`Esc` 或再按空格关闭

### 3.2 筛选栏（FilterPanel + RangeSlider）

- 分辨率与体积改用**一个轨道两个把手**的双向滑块 + **直方图**（全库分布，与当前条件无关）
- 每个档位配**两个数字输入框**（可直接输入），右侧写清单位，开口端显示「不限」
- 命中数实时更新（防抖 120ms），图片墙在松手/停顿 250ms 后刷新
- 已生效条件以标签形式列出，每个标签可单独删除；每个档位有独立的重置按钮
- 直方图数据来自后端一次性统计（按短边 100px 一档、体积按对数档），扫描完成后失效重取

### 3.3 顶栏（TopBar）

- 搜索框：按文件名/路径模糊搜索，输入防抖 300ms，`Esc` 清空
- 排序下拉：体积大→小、体积小→大、分辨率高→低、分辨率低→高、路径
- 右侧显示「库内 N 张 · 总体积 · 最后扫描时间」

### 3.4 扫描页

- **取消真正生效**：后端在扫描与指纹的循环里检查取消标记，返回已完成的数量
- 进度区显示吞吐（张/秒）与预计剩余时间
- 扫描结束显示：新增/更新/跳过/失败，以及所用时间
- 指纹阶段显示「已完成 / 总数」「失败 N」「预计剩余」

### 3.5 重复组

- 每组显示「这一组能省 X MB」
- 保留项旁边写明**为什么建议留它**（带作品 ID / 路径更短 / 收藏时间更早）
- 相似度用「N% 像」表达（`100 - 距离/64*100`）
- 底部加「只留这张，其余 N 张移入隔离区」一键操作

### 3.6 隔离区

- 每批可展开，列出具体文件（缩略图 + 文件名 + 体积）
- 「彻底清空」的二次确认里列出文件名（最多 10 个，其余显示「等 N 个文件」）
- 显示隔离区当前总占用

## 4. 性能规则（防止再次卡顿）

1. 滑块/输入框：**拖动中只更新计数**（防抖 120ms），松手后才整表刷新
2. 所有异步查询带**请求序号**，旧响应到达时直接丢弃（避免乱序覆盖）
3. 网格只渲染视口内的格子（已有的虚拟滚动保留）
4. 缩略图按 id 缓存 Blob URL，同屏不重复请求
5. 动画只用 `transform` / `opacity`，不触发重排

### 过程中发现并修掉的真问题

1. **缩略图生成跑在界面主线程上**（`get_thumb` 是同步命令）：一张 4000×6000 的图解码要几百毫秒，
   一屏几十张就是十几秒界面假死——这是用户反馈「拖滑块卡顿」的主要原因之一，
   不只是查询频繁。改为 `async` + `spawn_blocking` 离开主线程，并用信号量把并发限制到 6 张
   （否则几十张大图同时解码，内存会冲到几个 GB）。
2. **图库只能看到前 300 张**：后端早就支持分页，前端却固定 `offset: 0` 只取一页。
   现在滚到距底部 1.5 屏时自动加载下一批，并处理「加载途中筛选条件变了」的作废重试。
3. **扫描/指纹的「取消」按钮是死的**：只置了个标记，后台循环从不检查。
   现在扫描（枚举、读图片头、写库三处）与指纹（内容、视觉两处）都会检查，返回已完成数量。
4. **顶栏体积显示成 742160061.80 TB**：JS 位运算只有 32 位，`1 << 40` 实际等于 256。
   已在 `src/format.ts` 里统一用 `1024 ** n`，并写明原因。
5. 设置页的数字框被清空时，原本会把后端的 serde 原始报错甩给用户，现在给出人话提示。

## 11. 第五轮（2026-10-06）：窗口记忆 + 信息挪到底部

### 窗口位置/大小/最大化记忆

用官方 `tauri-plugin-window-state`（v2.5.0，要求 rustc ≥ 1.90，本机 1.99 满足），状态存在
`%APPDATA%\com.landslide.picsieve\.window-state.json`。两点刻意的选择：

1. **只记 POSITION / SIZE / MAXIMIZED**，不用默认的「全部」。默认集合里含 `VISIBLE`——
   万一程序在「窗口不可见」的状态下退出，下次启动会恢复成不可见，等于**打开后什么都没有**。
   这类坑宁可提前排除。
2. **窗口配置成 `visible: false`**，等前端第一帧画好再调 `show_main_window` 显示。
   否则会「先在默认位置闪一下，再跳到上次的位置」。Rust 侧另有 3 秒兜底：
   万一前端白屏没起来，也会把窗口显示出来，不让用户以为程序没启动。

验证（真窗口、Win32 量坐标）：

- 把窗口挪到 `130,95`、改成 `1180×800` → 正常关闭 → 重启：位置大小**一模一样**（差 0,0,0,0）
- 最大化 → 关闭 → 重启：`IsZoomed = true`，且窗口铺满屏幕工作区
  （3840×2160、200% 缩放；最大化窗口 3866×2106 = 工作区 + 每边 13px 的 DWM 隐形边框，属正常）

注意：测试用的脚本必须自己设成 **per-monitor DPI aware** 再量坐标，否则量到的是虚拟化坐标会误判；
也不能用 `Process.MainWindowHandle`——进程里有个 13×13 的可见辅助窗会被误选，要按面积挑主窗口。

### 库内信息挪到底部中间

`TopBar` 右侧只留排序；「库内 N 张 · 体积 · 上次扫描」移到底部信息栏的**正中间**，
底部栏改成 `1fr auto 1fr` 三栏，所以信息永远居中、不会因左右内容变宽而左右跑。
底部栏现在**常驻所有页签**（其他页签只有中间那条信息，不显示选中与「移到隔离区」）。

## 12. 第六轮（2026-10-06）：只看重复的误解、重复组平铺、翻页键

### 12.1 「搬走一张，另一张也不见了」——其实没搬，是筛选条件导致的

用户反馈：勾「有重复的」后单击一张、点移到隔离区，像是把**两张都搬走了**。

实测（沙箱里逐字节核对磁盘）：**只搬走了被选中的那一张**，另一张原地不动。
真正发生的是：「重复」是**成对**概念，A 被搬走后 B 就不再是重复图，
于是 B 从「只看重复」这个列表里掉出去——看起来像是被一起处理了。

处理方式：不改变行为（行为是对的），而是**把话说清楚**：

- 搬完的提示补一句「另有 N 张因为同伴被搬走、不再是重复图，从当前列表掉出去了（文件没动，去掉『有重复的』就能看到）」
- 筛选栏勾上「有重复的」时，下面直接显示同一句解释

### 12.2 重复组页：改成密集平铺，一屏尽量多组

原来是一组一屏、靠「上一组/下一组」翻，太慢。现在：

- 所有组**密集平铺**（自适应网格，宽屏 6 列），实测一屏能看 **36 组**（原布局约 4 组）
- 每组一个小卡片：编号、尺寸、能省多少、缩略图（保留的那张带橙色框与 ✓，一模一样的标「一样」）、建议理由、「其余 N 张移入隔离区」
- **点哪张就留哪张**（当场换保留标记，后端 `set_keeper` 同步），不认同默认建议时一次点击即可
- 滚到底自动加载下一批（每批 40 组）；`PgUp/PgDn/Home/End` 同样可用

同时修掉一个真 bug：`keepAs` 先替换数组元素、再取 `next[idx]`，取到的是**旧保留项**，
表现是「点了没反应」。测试从 DOM 的保留标记断言，正好抓住。

### 12.3 键盘翻页：PgUp / PgDn / Home / End（图库与重复组都支持）

- `PgUp/PgDn`：整屏翻页（留一行重叠），焦点格跟着走
- `Home`：回顶部
- `End`：**一路到底**——滚到最底并不断取下一批，直到全部加载完
- **打断**：滚滑轮、点鼠标、按其它键，立刻停止自动加载

### 12.4 顺带挖出并修掉的性能／稳定性问题

| 问题 | 现象 | 修法 |
|---|---|---|
| 后端用信号量限流 | 前端一口气要几十张时，每个排队请求占一条阻塞线程，实测**线程涨到 555、CPU 归零、缩略图再也不出** | 去掉后端信号量；限流改到**前端排队**（最多 6 张并发，队列超 400 条丢弃最老的） |
| 快速滚动疯狂请求缩略图 | 滚过的每个格子都去要一张，滚完 12 万张就排了十几万个请求，把后面的图全堵死 | 请求支持**取消**：格子滚出画面就跳过（排队中的也作废） |
| `files` 用深响应式 | 十万级记录每条都包成 Proxy，内存与访问开销翻几倍 | 改 `shallowRef`（整表替换，本来也不需要逐字段响应） |
| `×N` 角标每次整表重算 | 每来一批就遍历全部已加载项，总体 O(n²) | 改**增量维护**（按 content_hash 分组累加） |
| `End` 用 300 一批 | 12.9 万张要跑 430 趟，每趟还要按 OFFSET 跳行（12 万处单次 816ms） | `End` 改用 3000 一批 |

**实测对比（真实库 129,147 张）**：

| | 优化前 | 优化后 |
|---|---|---|
| `End` 加载完全部 | 30 秒才 4.35 万张（推算约 3 分钟） | **23 秒全部加载完** |
| 渲染进程内存 | 367 MB | **75–147 MB** |
| 应用线程数 | 555（卡死） | **49** |
